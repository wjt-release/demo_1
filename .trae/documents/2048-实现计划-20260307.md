# 2048 Web 版实现计划（Plan）

## 目标
实现一个可在浏览器中游玩的 2048（4×4）小游戏，包含完整的合并规则、计分、胜负判定，并提供手感良好的键盘与触摸操作，以及精致且有辨识度的 UI。

## 默认假设（后续可随时调整）
- 纯前端实现（不需要后端/账号/联网排行榜）。
- 桌面优先，同时适配移动端触控与小屏布局。
- 技术栈优先采用 React + TypeScript + Vite + Tailwind（符合项目初始化与前端工程化需求）。
- 玩法为经典 2048：每次移动后生成 1 个新块（2 的概率高于 4），同一次移动中每个格子最多合并一次。

## 交付物
- 产品文档：PRD（`.trae/documents/` 下）
- 技术架构文档：Technical Architecture（`.trae/documents/` 下）
- 可运行项目代码：本地 `npm/pnpm run dev` 可直接游玩
- 测试：核心棋盘逻辑的单元测试（Vitest）

## 实施步骤（按执行顺序）

### 1) 生成文档（必须先完成并等待确认）
1. 在 `.trae/documents/` 生成 PRD：明确页面（单页即可）、交互（键盘/触摸）、胜负条件、计分、复位、最佳分保存等。
2. 在 `.trae/documents/` 生成 Technical Architecture：说明前端分层（UI/状态/纯逻辑模块）、路由（如仅 `/`）、状态管理（zustand）、测试方案（Vitest）。
3. 通过通知请求你确认两份文档；你确认后才进入开发阶段。

### 2) 初始化前端工程
1. 使用 Vite 初始化 React + TS 模板（按环境选择 pnpm 或 npm）。
2. 安装依赖并确认能启动开发服务器。
3. 约定目录结构：
   - `src/pages`：页面（`GamePage`）
   - `src/components`：UI 组件（Board、Tile、Score、Controls、Modal）
   - `src/store`：zustand store（游戏状态、动作）
   - `src/utils`：纯逻辑（棋盘移动/合并/随机生成/判定）

### 3) 实现核心游戏逻辑（纯函数 + 可测试）
1. 定义数据结构：
   - `Board`：长度 16 的一维数组或 4×4 二维数组（存储数字或 0）。
   - `MoveResult`：新棋盘、得分增量、是否发生变化、是否生成新块、是否胜利/失败。
2. 实现关键算法：
   - 行/列抽取与归一化（向左合并作为基准，其他方向通过旋转/转置复用）。
   - 合并规则：相邻相同数字合并为 2×，并在本次移动中不再二次合并。
   - 生成新块：空位随机，值为 2/4（可配置概率）。
   - 判定：存在 2048 视为胜利；无空位且任意相邻不可合并视为失败。
3. 编写 Vitest 单元测试覆盖：
   - 合并边界（如 `[2,2,2,0] -> [4,2,0,0]`）
   - 不应连锁合并（如 `[2,2,4,4] -> [4,8,0,0]`）
   - 四方向一致性
   - 失败判定与胜利判定

### 4) 状态管理与动作（可扩展）
1. 建 zustand store：
   - `board`, `score`, `bestScore`, `status`（playing/won/lost）
   - `newGame()`, `move(direction)`, `keepPlaying()`（赢后继续可选）
2. 本地持久化：
   - `bestScore` 持久化到 `localStorage`
   - 可选：保存当前局面用于刷新恢复（可开关）

### 5) UI/交互实现（高质感、可玩性优先）
1. 单页布局：
   - 顶部：标题、当前分/最佳分、New Game
   - 中部：棋盘与方块动画
   - 底部：操作提示（键盘方向键/触摸滑动）
2. 视觉方向（在 PRD 中最终定稿）：
   - 选择强辨识度风格（例如复古 LCD/棋盘纹理/纸张印刷等），避免通用渐变模板化观感。
   - 颜色与字号统一用 token（CSS 变量或 Tailwind 主题映射）。
3. 动效与反馈：
   - 新块出现（scale-in）
   - 合并时短促弹跳（pop）
   - 无法移动时轻微抖动或提示
4. 输入支持：
   - 键盘方向键（含防止页面滚动）
   - 移动端滑动（pointer/touch，阈值判断方向）
   - 备用按钮（可选）用于无键盘设备
5. 可访问性：
   - 按钮可聚焦、可用键盘触发
   - 关键信息（分数、状态）对屏幕阅读器友好

### 6) 质量验证与交付检查
1. 运行单测与类型检查（如 `npm run test` / `npm run check` 视脚手架脚本而定）。
2. 手动验证：
   - 连续快速输入不会破坏状态
   - 赢/输弹窗与继续/重开逻辑正确
   - 移动端滑动手势准确、不会误触页面滚动
3. 启动开发服务器并提供可预览链接，确认交互无明显瑕疵。

## 里程碑与退出条件
- 文档阶段：PRD 与 Technical Architecture 通过确认。
- 开发阶段：核心逻辑单测通过 + UI 可完整游玩 + 本地最佳分持久化生效。
